# Product Roadmap

## Phase 1: Core Information Architecture — COMPLETE

- **Central Knowledge Gateway:** MCP server with plugin registration and tool routing. *(SPEC-001)*
- **Bundle Ingestion Pipeline:** Two-phase pipeline — processors write, observers react. *(SPEC-001, SPEC-003)*
- **Embedded Storage Engine:** SQLite with `sqlite-vec` and JSON1, plugin-scoped record types, indexed columns. *(SPEC-001, SPEC-002)*
- **Trivial Plugin Proof-of-Concept:** Markdown semantic processor with chunking, embedding, and search. *(SPEC-001)*
- **Plugin Data Contracts:** Record type system with schemas, discovery tool, cross-plugin queries. *(SPEC-002)*
- **Plugin Developer Guide:** Documentation for building plugins — interfaces, storage modes, record types. *(SPEC-002, SPEC-003)*

## Phase 2: Intelligence & Weighting — COMPLETE

- **Usage-Based Ranking:** Cumulative moving average scoring with magnitude signals (-5 to +5). *(SPEC-004)*
- **Information Decay:** Plugin-declared decay half-life on record types, computed at query time. *(SPEC-004)*
- **Document Lifecycle:** In-place updates (`update_payload`) and wipe-and-replace (`delete_by_uri`). *(SPEC-004)*
- **Tombstoning:** Flag bad documents out of results without deletion, reversible. *(SPEC-004)*
- **Idempotent Ingestion:** Content hashing, plugin versioning, and IngestionContext for smart re-ingestion decisions. *(SPEC-005)*
- **Plugin Lifecycle Management:** Dynamic registration/unregistration at runtime, filtered event subscriptions (topic-based + fire hose), persistent plugin state. *(SPEC-006)*
- **Semantic Type Routing:** Three-type model (semantic type, media type, record type), registration-time routing, available vs enabled activation model. *(SPEC-008)*
- **Record Type Rename:** Renamed `doctype` → `record_type` throughout codebase — column, indexes, APIs, tests, and docs. *(SPEC-009)*

## Phase 3: Reliability & Extensibility — IN PROGRESS

- **Reliability Seeding:** Three-layer initial quality scoring — ingest hint (from caller), plugin-declared default on `RecordTypeSpec`, platform default (0.0). Seeds `usage_score` at ingestion time so high-quality sources rank higher immediately. Replaces the original inline Librarian concept (ADR-006). *(SPEC-007 — COMPLETE)*
- **Multi-Tenancy & Metadata Search:** Per-tenant SQLite file sharding via `TenantStorageManager`. Each tenant gets its own `data.sqlite` shard — KNN operates on exactly the right dataset by construction. Scatter-gather cross-tenant queries. Metadata search via `json_extract` equality filters on the existing `metadata` column. Optional vector query (weight-ranked retrieval when query is omitted). Plugin developer guide updated: plugins are tenant-unaware, use `bundle.storage`. *(SPEC-010 — COMPLETE)*
- **Document Segments:** Formal parent-child hierarchy on the `documents` table via `parent_id` column. Parents are metadata containers (no vector, no weight). Segments are searchable, ratable children. Aggregate parent scoring computed at query time (AVG of children). Cascade delete for parents, surgical `delete_by_id` for segments. URI convention for segment naming. Segment ordering guaranteed by insertion order (`ORDER BY id`). MarkdownPlugin migrated to parent-child model. *(SPEC-011 — COMPLETE)*
- **Structured Ingestion Contracts:** A validated write path that lets external providers — AI agents or deterministic tools — push **pre-refined records** into the catalog, validated against a JSON Schema at the boundary. Shipped as `submit_structured` (batch) plus a canonical `write_record` toolkit that is the **single validation choke point** (framework and plugins both write through it; every record write is schema-validated). **First schema enforcement** — `RecordTypeSpec.schema` is now mandatory and enforced, not advisory. Clarified the three-type model (`media_type` / `semantic_type` / `record_type`); `metadata` stored 1:1 with the payload for MongoDB portability. IDL is JSON Schema (Protobuf/Pydantic rejected). Raw-content-by-value folded in; framework-owned decoding rejected. Foundational primitive for Meta-Plugins and agent-populated plugins. *(SPEC-012 — COMPLETE; see ADR-011)*
- **Curator (the *marker* — a host for pluggable curation strategies):** Async, LLM-based background process that keeps the catalog coherent by running **curation strategies**. Out of the box it ships two — **semantic deduplication** (same fact across different URIs) and **conflict detection** (contradicting facts) — both styles of curation that keep the catalog free of redundancy and contradiction. Each strategy either **tombstones (reversible)** or **marks the item for human consideration**. This is the surviving form of the mission's "validation gate" differentiator (the inline Librarian was retired in ADR-006 in favor of background curation). **Its autonomous action is tombstone only — it never hard-deletes.** **Pluggable from day one:** the Curator is architected as a *host* for curation strategies from the start, not a fixed process that's generalized later — dedup and conflict detection are simply the first two strategies shipped on that architecture. A **`CurationStrategy` interface** (alongside `IngestProcessor` / `IngestObserver`) is part of the initial design, so teams can add their own strategies and **governance/compliance policies** (freshness, regulatory, domain- or org-specific rules) without touching core. **Independent — "not blocked by anything" (ADR-006).** Service Profile provides/consumes edge-reconciliation is one such strategy, not a dependency. Capstone item, several iterations to dial in.
  - *Direction (to settle at spec time):* Runs as its **own independent process on its own cadence** (sweep-based), **fully decoupled from ingestion — no ingestion-path trigger, so ingestion never slows.** **Action configurable per information type/level** — autonomous **tombstone** vs. **mark for consideration**; high-reliability/"golden" docs protected; confidence-tiered. **v1 exploits reversible tombstone:** auto-tombstone a few safe info types → an instantly working system, with the audit report + restore below as the safety net. **v2 adds the pre-action review queue** for higher-stakes types. Paired with **Curation Audit & Review** (below).
  *(Future — see ADR-006)*
- **Reaper (tombstone retention / compaction — the *collector*):** Deterministic, **no-LLM** system-hygiene process that **permanently deletes items tombstoned longer than a configurable retention threshold** (per info type / tenant, incl. "never"), bounding datastore growth. **This is the only place hard delete happens, and it is safe by construction** — every deletion had a reversibility window first. Proven production pattern (Kafka tombstone retention / log compaction, soft-delete GC). **The retention threshold *is* the restore window:** a tombstoned item is recoverable until the Reaper collects it. Small, independent, deterministic — depends on nothing (tombstone already exists; likely needs a `tombstoned_at` timestamp on `doc_weights`) and could be **pulled forward cheaply, ahead of the Curator.** Drains the tombstone queue the Curator fills. *(Future)*
- **Curation Audit & Review:** Visibility + human-in-the-loop surface for automated/agent-driven curation, **built in this priority order:** (1) an **audit report of what's been tombstoned** with one-click **restore** (un-tombstone is already reversible) — surfacing each item's **scheduled reap date** so humans can restore before the Reaper permanently removes it — plus a **notification/subscription layer** so external systems (Slack/Teams/email/webhooks) can subscribe to curation events (an outward-facing event stream, distinct from the internal `IngestObserver`); then (2) a **review queue** (second admin page) where the Curator's "mark for consideration" recommendations wait for human approval before taking effect. **Generalized beyond the Curator:** Service Profile agent inferences and any future auto-curation feed the same report/notification/review layer. Sequenced alongside the Curator as its visibility + disposition surface. *(Future)*
- **Meta-Plugins / Chained Processing:** Observer-triggered secondary ingestion enabling complex processing pipelines (e.g., dependency audit across code + POM output). Builds on Structured Ingestion Contracts as its submission mechanism. First concrete driver: agent synthesis of Service Profiles (Phase 4). *(Future — see ADR-007)*

## Phase 4: Scale & Integrations

- **Service Profile Plugin(s):** A machine-readable service catalog living inside Team Mind — per service: dependencies (internal + external), schemas/data shapes, **provides/consumes** integration contracts, and persisted data. Hybrid population: deterministic extractors (POM/`package.json`/OpenAPI/`.proto`/migrations) self-extract ground-truth facts; an AI agent supplies **inferred** facts (real consumers, intent) via Structured Ingestion Contracts. Stored as parent (service) + segments (facets) with reliability tiering — deterministic facts high/no-decay, inferred facts lower/decaying. Starts as a single plugin with snap-in per-language extractors; graduates to a per-language plugin family. **Depends on SPEC-012; drives Meta-Plugins (agent synthesis); provides the Curator a curation strategy (provides/consumes edge reconciliation) — not a dependency in either direction.**
- **Database Migration:** Move from SQLite to self-hosted MongoDB (or similar) for robust vector and document storage at scale.
- **Access Control & RBAC:** Add security layers for different project access levels.
- **MS Teams Integration:** Bot for querying and contributing knowledge directly from chat.
- **Additional Tooling Integrations:** Other workspace and developer tool integrations as the platform matures.
- **Frontend UI:** Lightweight JavaScript UI for human browsing and management of the knowledge graph.
